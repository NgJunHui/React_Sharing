00

Overview

Every web page is built from three languages. They are separate concerns with separate jobs, and everything else in this session sits on top of them.

Structure

HTML

The content and its meaning. Headings, paragraphs, inputs, buttons. No styling, no behaviour.

Presentation

CSS

How it looks. Colour, spacing, size, position, responsiveness. Selects elements and applies rules.

Behaviour

JavaScript

What happens. Responds to clicks, updates content, talks to APIs. The only one of the three that is a programming language.

The same button, expressed in all three. Each layer is independent, and each can be changed without touching the others. 

<!-- HTML: what it is -->
<button id="save" class="btn">Save</button>

/* CSS: how it looks */
.btn {
  background: #141B4D;
  color: white;
  padding: 8px 16px;
  border-radius: 6px;
}

// JavaScript: what it does
document.getElementById('save').addEventListener('click', () => {
  saveForm();
});

Why frameworks exist

Writing plain JavaScript works for a page or two. Once an application has many screens sharing data, keeping the page in sync with that data by hand becomes the bulk of the work, and the bulk of the bugs. Frameworks exist to take that job over.

Figure 1. You update the data. The framework works out what the page should look like and updates it for you.

The main frameworks

They solve the same problem in different styles. The concepts move across: learn one properly and the others are mostly new syntax.

Framework Backed by Character
React Meta A library, not a full framework. You pick your own router and data layer. Largest ecosystem
Angular Google Full framework. Routing, forms, and HTTP included and opinionated. TypeScript by default
Vue Community Middle ground. Gentle learning curve, official router and store available
Svelte Community Compiles away at build time. Less runtime code shipped to the browser
Our choice

We use React. Everything from here on is React, but the underlying ideas of components, state, and one way data flow apply to all of them.

What is TypeScript

TypeScript is JavaScript with type annotations added. It is a superset: every valid JavaScript file is already valid TypeScript. You add types where they help, and a checker catches mistakes while you write rather than when a user hits them.

Figure 2. TypeScript adds a layer on top. Nothing is taken away.

JavaScript

Nothing complains until this runs, and then only if that exact line is reached. 

function total(price, qty) {
  return price * qty;
}

total('10', 3);       // "101010"
total(10);            // NaN
total(10, 3, 7);      // silently ignored
TypeScript

All three mistakes are flagged in the editor, underlined in red, before the file is even saved. 

function total(price: number, qty: number) {
  return price * qty;
}

total('10', 3);       // string not assignable
total(10);            // expected 2 arguments
total(10, 3, 7);      // expected 2, got 3

What it adds

01

Errors while you type

Typos in property names, wrong argument counts, and values that might be undefined surface in the editor instead of the browser.

02

Autocomplete that knows the shape

Type a dot and the editor lists exactly what exists on that object. This alone changes how fast you can move in unfamiliar code.

03

Safe renaming

Rename a field and every usage updates. Miss one and it is a compile error, not a bug discovered in production.

04

Types as documentation

A function signature tells you what goes in and what comes out. It cannot drift out of date the way a comment can.

Important

Types are checked at build time and then removed. The browser runs plain JavaScript and knows nothing about them. TypeScript catches mistakes before shipping, but it does not validate anything while the app is running.

01

What is a Component

A component is a function that takes an object of inputs and returns a description of UI. That is the whole idea. Everything else in React is built on top of it. 

// A component is a function. Input: props. Output: UI description.
function StatusBadge({ status, label }) {
  return <span className={`badge badge--${status}`}>{label}</span>;
}

// Used like an HTML tag. Capitalised name means "component".
<StatusBadge status="active" label="Running" />
<StatusBadge status="failed" label="Build failed" />
01

It is just a function

No class required, no framework magic in the signature. If you can write a function that returns a value, you can write a component.

02

It must be pure

Same props in, same output out. No mutating inputs, no writing to globals during render. Side effects belong in useEffect.

03

Capitalisation matters

<button> is a DOM element. <Button> is your component. React uses the case of the first letter to decide.

The composition tree

Components nest. A page is not one large function, it is a tree of small ones. This is the same instinct as breaking a large service class into smaller collaborators.

Figure 1. A page is a tree. Leaf components are small, reusable, and know nothing about the page they sit in.

02

JSX

JSX looks like HTML inside JavaScript. It is not a template language and it is not string interpolation. It is syntax sugar that the build step compiles into ordinary function calls.

What you write 
const ui = (
  <div className="card">
    <h2>{title}</h2>
    <Badge tone="success" />
  </div>
);
What the compiler emits 
const ui = jsx('div', {
  className: 'card',
  children: [
    jsx('h2', { children: title }),
    jsx(Badge, { tone: 'success' })
  ]
});

Because it compiles to a function call, the result is a plain JavaScript object. You can store it in a variable, return it from a conditional, or put it in an array. That is why there is no special loop or if syntax in JSX: you use the JavaScript you already have.

The rules that trip people up

// 1. className, not class. "class" is a reserved word in JavaScript.
<div className="container" />

// 2. Attributes are camelCase.
<input onChange={handleChange} maxLength={40} tabIndex={0} />

// 3. Braces switch from markup back into JavaScript.
<p>Total: {items.reduce((sum, i) => sum + i.price, 0)}</p>

// 4. Conditionals use normal JS operators, not directives.
{isLoading && <Spinner />}
{error ? <ErrorBanner message={error} /> : <OrderList data={data} />}

// 5. Lists use .map(). Each item needs a stable "key".
<ul>
  {orders.map((order) => (
    <li key={order.id}>{order.reference}</li>
  ))}
</ul>

// 6. One root element. Use a fragment <>...</> when you do not want a wrapper div.
<>
  <Header />
  <Content />
</>
On keys

key tells React which item is which between renders. Use the record identifier from your API. Do not use the array index if the list can be reordered, filtered, or have items removed, because React will then reuse the wrong element and you get stale or mismatched rows.

03

Props and State

Two ways data enters a component. Props come from the parent and are read only. State is owned by the component and can change. Almost every React design question reduces to deciding which one a piece of data should be.

Props

Passed in, never written to

Think of them as function arguments. The parent controls the value. A component that only takes props and renders is predictable and trivial to test. 

function Price({ amount, currency }) {
  return <span>{currency} {amount.toFixed(2)}</span>;
}

// Parent decides the values
<Price amount={42.5} currency="SGD" />
State

Owned locally, triggers re-render

Calling the setter schedules a re-render. The variable itself is never mutated. Never assign to it directly, React will not notice. 

function Search() {
  const [query, setQuery] = useState('');

  return <input
    value={query}
    onChange={(e) => setQuery(e.target.value)}
  />;
}

Data flows down, events flow up

React is one directional. A parent hands data to a child as a prop. If a child needs to change that data, the parent also hands it a callback. The child calls it, the parent updates its own state, and the new value flows back down.

Figure 2. The child never mutates the value it was given. It reports an intention and lets the owner decide. 

// Parent owns the state and passes both value and setter down.
function OrderFilters() {
  const [status, setStatus] = useState('open');

  return (
    <>
      <StatusDropdown value={status} onChange={setStatus} />
      <OrderTable status={status} />
    </>
  );
}

// Child is "controlled": it renders what it is told and reports changes.
function StatusDropdown({ value, onChange }) {
  return (
    <select value={value} onChange={(e) => onChange(e.target.value)}>
      <option value="open">Open</option>
      <option value="closed">Closed</option>
    </select>
  );
}

State updates are immutable

React compares the old value to the new one by reference. If you mutate an array or object in place, the reference does not change and React concludes nothing happened. Always produce a new value.

Will not re-render 
items.push(newItem);
setItems(items);          // same array reference

user.name = 'Wei Ling';
setUser(user);            // same object reference
Correct 
setItems([...items, newItem]);

setUser({ ...user, name: 'Wei Ling' });

// Depending on previous value? Use the function form.
setCount((prev) => prev + 1);

Derived state is not state

If a value can be calculated from existing props or state, calculate it during render. Storing it separately means two sources of truth that will drift apart.

Redundant 
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

// Now every setItems must remember
// to also call setTotal. It will not.
Single source of truth 
const [items, setItems] = useState([]);

// Just compute it. It cannot go stale.
const total = items.reduce(
  (sum, i) => sum + i.price, 0
);
04

Rendering and Effects

Understanding when your function body runs removes most React confusion. A component function is called again on every render, and that happens more often than you would expect.

The render cycle

Figure 3. React re-runs the function, compares the returned description to the previous one, and writes only the differences to the DOM.

Key point

Re-render does not mean the DOM is rebuilt. It means your function is called again. React then compares and touches the DOM as little as possible. That is why re-rendering is cheap and why you should not fight it.

useEffect: escaping to the outside world

Render must be pure, so anything that reaches outside React goes in an effect: network calls, subscriptions, timers, direct DOM measurement, logging. Effects run after the DOM has been updated. 

useEffect(() => {
  // 1. The effect body: runs after render is committed
  const socket = connectToOrderFeed(orderId);
  socket.on('update', setOrder);

  // 2. The cleanup: runs before the next effect and on unmount
  return () => socket.close();

// 3. The dependency array: re-run only when these values change
}, [orderId]);
Dependency array When the effect runs
[] Once after the first render only
[orderId] After first render, then whenever orderId changes
omitted entirely After every single render. Usually a bug
Most common mistake

Reaching for useEffect to compute a value. If you find yourself setting state inside an effect that depends on other state, you almost certainly want a plain calculation during render instead. Effects are for synchronising with systems outside React.

Custom hooks

A custom hook is a function starting with use that calls other hooks. It is how you extract stateful logic without extracting UI. This is the closest analogue to a service class. 

// Extracted once, reused everywhere. No UI inside.
function useDebounced<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);

  return debounced;
}

// Consumer stays clean
function OrderSearch() {
  const [query, setQuery] = useState('');
  const debouncedQuery = useDebounced(query, 300);

  const { data } = useOrders({ search: debouncedQuery });
  // ...
}
05

Event Handling

Events in React look like inline HTML handlers but behave like properly scoped JavaScript. You attach a function reference, not a string. 

// Pass the function. Do not call it.
<button onClick={handleSave}>Save</button>        // correct
<button onClick={handleSave()}>Save</button>      // runs during render

// Need to pass an argument? Wrap it in an arrow function.
<button onClick={() => handleDelete(order.id)}>Delete</button>

// Forms: prevent the browser's default full page reload.
function handleSubmit(event) {
  event.preventDefault();
  submitOrder(formValues);
}

<form onSubmit={handleSubmit}> ... </form>
01

Synthetic events

React wraps the native event in its own object with a consistent API across browsers. event.target and preventDefault() work exactly as you expect.

02

Handlers are props

onClick on your own component is just a prop named onClick. There is nothing special about it until you forward it to a real DOM element.

03

Naming convention

Prop is onSomething, the function passed to it is handleSomething. Consistent naming makes the direction of the call obvious at a glance.

06

How a Page is Built

A page is a component that a router renders for a given URL. It is responsible for fetching what it needs and arranging smaller components into a layout. It should contain very little logic of its own.

From URL to rendered screen

Figure 4. The page is the only layer that knows about the route and the data source. Everything below it receives props.

A realistic page component

import { useParams } from 'react-router-dom';
import { Stack, Alert, Skeleton } from '@mui/material';
import { useOrder } from '@/features/orders/hooks/useOrder';
import { OrderSummary } from '@/features/orders/components/OrderSummary';
import { OrderTimeline } from '@/features/orders/components/OrderTimeline';
import { PageHeader } from '@/components/PageHeader';

export function OrderDetailPage() {
  const { id } = useParams();
  const { data: order, isLoading, error } = useOrder(id);

  // Guard clauses first. Same instinct as early returns in a handler.
  if (isLoading) return <Skeleton variant="rectangular" height={320} />;
  if (error) return <Alert severity="error">{error.message}</Alert>;
  if (!order) return <Alert severity="info">Order not found</Alert>;

  // Happy path: arrange components, pass data down.
  return (
    <Stack spacing={3}>
      <PageHeader
        title={`Order ${order.reference}`}
        status={order.status}
      />
      <OrderSummary order={order} />
      <OrderTimeline events={order.events} />
    </Stack>
  );
}

Three kinds of component

Page

Route level

Reads route params, calls data hooks, handles loading and error branches, composes the layout. One per route.

Feature

Domain aware

Knows what an order is. Lives in the feature folder. Reusable within that feature but not outside it.

Common

Domain agnostic

A button, a data table, an empty state. Knows nothing about orders or users. This is what lives in Storybook.

07

State Management

Not all state is the same. Choosing where a piece of state lives is the main architectural decision you make on the frontend, and getting it wrong is the main source of tangled code.

Four categories

01

Local UI state

Is this dropdown open, what is typed in this input, which tab is active. Owned by one component, dies with it.

useState

02

Shared UI state

Theme, current user, sidebar collapsed. Needed in many places, does not come from the server, changes rarely.

Context or a store

03

Server state

A copy of data that lives in your database. It can go stale, needs refetching, caching, and loading states. It is not really your state.

React Query or similar

04

Form state

Field values, validation errors, dirty and touched flags, submission status. Distinct enough to deserve its own library.

React Hook Form

Rule of thumb

Start with useState in the component that needs it. Move it up only when a sibling needs the same value. Reach for Context or a store only when passing props through more than about three levels becomes noise. Most teams reach for global state far too early.

Lifting state up

When two components need the same value, move that value to their closest common parent and pass it down to both.

Figure 5. Two copies of the same value will eventually disagree. One owner, many readers.

Context for genuinely global values

// 1. Create the context with a typed default.
interface AuthContextValue {
  user: User | null;
  signOut: () => void;
}

const AuthContext = createContext<AuthContextValue | undefined>(undefined);

// 2. Provide it near the root of the tree.
export function AuthProvider({ children }: { children: ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const signOut = () => setUser(null);

  return (
    <AuthContext.Provider value={{ user, signOut }}>
      {children}
    </AuthContext.Provider>
  );
}

// 3. Consume through a custom hook that fails loudly if misused.
export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used inside AuthProvider');
  return ctx;
}
Context is not a database

Every component consuming a context re-renders when its value changes. Do not put fast changing data like a text input value in a context that wraps the whole app. Use it for values that change rarely: the signed in user, the theme, feature flags.

08

Data Fetching

You know the request and response side already. What is new is that the answer arrives after the screen has already rendered, so every fetch has at least three visual states you must design for.

Figure 6. Every screen that talks to an API needs all three. Missing the loading state is the most common frontend review comment.

The manual version

Worth seeing once so the library version is not magic. Note the cancellation guard: if the component unmounts or the id changes mid flight, you must not write the stale response into state. 

function useOrderManual(id: string) {
  const [data, setData] = useState<Order | null>(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    let cancelled = false;
    setIsLoading(true);

    fetch(`/api/orders/${id}`)
      .then((res) => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then((json) => { if (!cancelled) setData(json); })
      .catch((err) => { if (!cancelled) setError(err); })
      .finally(() => { if (!cancelled) setIsLoading(false); });

    // Cleanup guards against writing a stale response.
    return () => { cancelled = true; };
  }, [id]);

  return { data, isLoading, error };
}

What a data library gives you

The manual version is correct but incomplete. It has no caching, no deduplication, no retry, no refetch on window focus, and no way for two components to share one request. That is what React Query handles. 

import { useQuery } from '@tanstack/react-query';

export function useOrder(id: string) {
  return useQuery({
    queryKey: ['order', id],           // cache identity
    queryFn: () => fetchOrder(id),      // how to get it
    staleTime: 30_000,                // treat as fresh for 30s
  });
}

// Two components, one network request. The cache deduplicates.
function Summary({ id }) { const { data } = useOrder(id); /* ... */ }
function Sidebar({ id }) { const { data } = useOrder(id); /* ... */ }

Typing the boundary

Important

TypeScript does not validate anything at runtime. Annotating a response as Order is a promise you are making to the compiler, not a check. If the API changes shape, the types will still say everything is fine while the app breaks. 

// This is an assertion, not a validation. It is a lie if the API changed.
const order = await res.json() as Order;

// Validate at the boundary if the contract is not fully under your control.
import { z } from 'zod';

const OrderSchema = z.object({
  id: z.string(),
  reference: z.string(),
  status: z.enum(['open', 'closed', 'cancelled']),
  total: z.number(),
});

type Order = z.infer<typeof OrderSchema>;   // type derived from schema

export async function fetchOrder(id: string): Promise<Order> {
  const res = await fetch(`/api/orders/${id}`);
  if (!res.ok) throw new Error(`Failed to load order ${id}`);
  return OrderSchema.parse(await res.json());  // throws on mismatch
}
09

TypeScript Basics

TypeScript is JavaScript with a type checker bolted on at build time. Every type annotation is erased before the code runs. Nothing you write in types exists in the browser.

Figure 7. Types are a development time contract. At runtime the browser sees plain JavaScript. 

// Primitives. Usually inferred, so you rarely write these.
const reference: string = 'ORD-8821';
const total: number = 149.9;
const isPaid: boolean = true;

// Arrays
const tags: string[] = ['urgent', 'export'];

// Object shape
interface Order {
  id: string;
  reference: string;
  total: number;
  note?: string;              // optional: string | undefined
  readonly createdAt: string;   // cannot be reassigned
}

// Union: one of a fixed set. Far better than a bare string.
type OrderStatus = 'open' | 'closed' | 'cancelled';

// Function signature
function applyDiscount(order: Order, percent: number): Order {
  return { ...order, total: order.total * (1 - percent / 100) };
}

interface or type

interface

For object shapes. Can be extended and merged. Slightly better error messages. Use this by default for props and models. 

interface BaseEntity {
  id: string;
  createdAt: string;
}

interface Order extends BaseEntity {
  reference: string;
  total: number;
}
type

For everything an interface cannot express: unions, intersections, tuples, mapped and conditional types, aliasing a primitive. 

type Status = 'open' | 'closed';

type Coord = [number, number];

type WithAudit<T> = T & {
  updatedBy: string;
};

Narrowing

A union type must be narrowed before you can use the members specific to one branch. TypeScript follows normal control flow to do this, so ordinary if checks are enough. 

type Result =
  | { kind: 'success'; order: Order }
  | { kind: 'failure'; message: string };

function describe(result: Result): string {
  if (result.kind === 'failure') {
    return result.message;      // TS knows: failure branch
  }
  return result.order.reference; // TS knows: success branch
}

// Optional values must be checked before use.
function initial(name?: string) {
  if (!name) return '?';
  return name[0].toUpperCase();  // safe: name is string here
}
Avoid

any disables checking for that value and everything it touches. If you genuinely do not know a type, use unknown instead: it forces you to narrow before use, which is the entire point.

TypeScript in React

In practice, ninety percent of the TypeScript you write in a React codebase is typing props. Get that right and the rest is mostly inference. 

import { type ReactNode } from 'react';

// Props interface. Convention: ComponentName + "Props".
interface OrderCardProps {
  order: Order;

  onSelect,
  actions,

Typing hooks

// Inferred from the initial value. No annotation needed.
const [query, setQuery] = useState('');            // string
const [count, setCount] = useState(0);              // number

// Annotate when the initial value does not tell the whole story.
const [order, setOrder] = useState<Order | null>(null);
const [items, setItems] = useState<Order[]>([]);       // otherwise never[]

// Refs pointing at DOM nodes.
const inputRef = useRef<HTMLInputElement>(null);

// Event handlers. Let React's types do the work.
function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);
}

function handleSubmit(e: React.FormEvent<HTMLFormElement>) {
  e.preventDefault();
}

Making bad states unrepresentable

This is the payoff. A well designed union means the compiler rejects combinations that should never exist, so you never have to write a defensive check for them.

Allows nonsense 
interface Props {
  isLoading: boolean;
  error?: string;
  data?: Order;
}

// Nothing stops this:
<View isLoading error="x" data={o} />
Only valid shapes compile 
type Props =
  | { status: 'loading' }
  | { status: 'error'; message: string }
  | { status: 'ready'; data: Order };

// The compiler rejects the impossible
// combinations outright.
11

Utility Types

Built in helpers that derive one type from another. They keep types in sync automatically, so changing the source model updates everything derived from it. 

interface Order {
  id: string;
  reference: string;
  status: OrderStatus;
  total: number;
  customerId: string;
}

// Partial: every field optional. Ideal for PATCH payloads.
type OrderPatch = Partial<Order>;

// Pick: keep only what you name. Ideal for list rows.
type OrderListItem = Pick<Order, 'id' | 'reference' | 'status'>;

// Omit: everything except what you name. Ideal for create payloads.
type NewOrder = Omit<Order, 'id'>;

// Required: strip all optionality.
type CompleteOrder = Required<Order>;

// Record: build a lookup keyed by a union.
type StatusLabels = Record<OrderStatus, string>;

const labels: StatusLabels = {
  open: 'Open',
  closed: 'Closed',
  cancelled: 'Cancelled',
  // Miss one and the compiler complains. Add a status later
  // and every Record using it fails until you handle it.
};

// ReturnType: derive from an existing function, no manual duplication.
type OrderQuery = ReturnType<typeof useOrder>;
Utility Effect Typical use
Partial<T> All fields optional Update payloads, default merging
Required<T> All fields mandatory After validation or defaulting
Pick<T, K> Subset of fields Lightweight list or summary views
Omit<T, K> All except named fields Create payloads without server fields
Record<K, V> Map from key union to value Exhaustive label or config lookups
ReturnType<F> Result type of a function Deriving hook return types

React Hook Form

Forms are the one place where the plain React approach genuinely does not scale. React Hook Form keeps field values out of React state, so typing in one field does not re-render the entire form.

Hand rolled, twelve fields 
const [values, setValues] = useState({...});

A typed form end to end

import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';
import { TextField, Button, Stack } from '@mui/material';

// 1. Schema is the single source of truth for shape and rules.
const schema = z.object({
  reference: z.string().min(3, 'At least 3 characters'),
  quantity:  z.coerce.number().int().positive('Must be greater than 0'),
  email:     z.string().email('Enter a valid email'),
});

// 2. Type is derived, never written twice.
type OrderForm = z.infer<typeof schema>;

export function CreateOrderForm({ onCreated }: Props) {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<OrderForm>({
    resolver: zodResolver(schema),
    defaultValues: { reference: '', quantity: 1, email: '' },
  });

  // 3. onSubmit only runs if validation passed. Values are typed.
  const onSubmit = async (values: OrderForm) => {
    const created = await createOrder(values);
    onCreated(created);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)} noValidate>
      <Stack spacing={2}>
        <TextField
          label="Reference"
          {...register('reference')}
          error={!!errors.reference}
          helperText={errors.reference?.message}
        />
        <TextField
          label="Quantity"
          type="number"
          {...register('quantity')}
          error={!!errors.quantity}
          helperText={errors.quantity?.message}
        />
        <Button type="submit" variant="contained" disabled={isSubmitting}>
          {isSubmitting ? 'Creating...' : 'Create order'}
        </Button>
      </Stack>
    </form>
  );
}

Storybook and Common Components

Storybook runs components in isolation, outside the app, with no routing and no backend. It is a workshop for building a component and a catalogue for finding one that already exists.

01

Build in isolation

No need to log in, navigate three pages, and create test data to see an error state. Render it directly with the props you want.

02

Document by example

A story is executable documentation. It cannot go stale the way a wiki page does, because it fails when the component changes.

03

Prevent duplication

Check Storybook before writing a component. The reason we have four slightly different date pickers is that nobody looked first.

A story file

import type { Meta, StoryObj } from '@storybook/react';
import { StatusBadge } from './StatusBadge';

const meta: Meta<typeof StatusBadge> = {
  title: 'Common/StatusBadge',
  component: StatusBadge,
  args: { label: 'Open', status: 'open' },   // shared defaults
};
export default meta;

type Story = StoryObj<typeof StatusBadge>;

// Each export is one state of the component.
export const Open: Story = {};

export const Cancelled: Story = {
  args: { label: 'Cancelled', status: 'cancelled' },
};

export const LongLabel: Story = {
  args: { label: 'Pending third party confirmation', status: 'open' },
};

What belongs in the common library

Yes
  • Knows nothing about orders, users, or any domain
  • All data arrives through props
  • Fetches nothing and reads no global state
  • Used in at least two features
  • Has a story covering its meaningful states
No
  • Imports a domain type such as Order
  • Calls an API or a query hook internally
  • Reads route params or app context
  • Used in exactly one place, speculatively generalised

Import direction

Features may import from components, hooks, lib, utils. Those must never import from a feature. One way only.

Vite and the Toolchain

Browsers cannot run TypeScript, JSX, or bare module imports. A build tool translates your source into something they can execute. Vite does that fast enough to feel instant.

Figure 9. In development Vite serves modules on demand. For production it bundles everything into static files.

File What it controls
package.json Dependencies and the scripts you run
package-lock.json Exact resolved versions. Commit it, never edit it
tsconfig.json Compiler strictness and path aliases
vite.config.ts Plugins, dev server proxy, build output
.eslintrc / eslint.config.js Lint rules enforced in CI
node_modules/ Installed packages. Never commit this

Environment variables

// .env.development
VITE_API_BASE_URL=http://localhost:8080/api

// Only names prefixed with VITE_ are exposed to the client.
const baseUrl = import.meta.env.VITE_API_BASE_URL;
Security

Everything in a frontend bundle is public. Anyone can open DevTools and read it. Never put an API secret, a signing key, or a database credential in a VITE_ variable. If it must stay secret, it belongs on your side of the wire.

React DevTools

A browser extension that adds React aware panels to DevTools. Without it you are inspecting compiled DOM output. With it you inspect the component tree and its live state.

Install

Available for Chrome and Firefox as React Developer Tools. Once installed, two new tabs appear in DevTools on any React page: Components and Profiler.

Image placeholder

Screenshot of the React DevTools Components tab on one of our pages, with a component selected so its props and hooks are visible in the right hand panel.

assets/react-devtools-components.png

Figure 10. Component tree on the left, props and hook state on the right, editable live.

01

Inspect the tree

See the actual component hierarchy with your own component names, not a wall of anonymous divs. Select any node to see the props it received.

02

Read and edit state live

Every hook is listed in order. You can change a value directly in the panel and watch the UI respond, which is the fastest way to reproduce an edge case.

03

Find the owner

When a prop has the wrong value, walk up the tree until you find the component that produced it. That is where the bug is, not where the symptom appeared.

04

Highlight updates

A setting that flashes a border around components as they re-render. Useful for confirming whether something is rendering when you did not expect it to.

A practical debugging order

1

Is the data arriving

Network tab. Check the status code and the response body. If the request failed or returned an unexpected shape, stop here. This is your home territory.

2

Is it in state

DevTools Components tab. Select the component that owns the fetch and read its hook values. If the response was fine but state is empty, the bug is between them.

3

Is it reaching the child

Select the child that should display it and read its props. A correct parent with an empty child prop means the value is not being passed, or is being passed under a different name.

4

Is it being rendered

Props are right but nothing appears. Look for a conditional above the render, a filter that removes everything, or a CSS rule hiding the element. Check the Elements tab.

Errors you will see early

Message What it actually means
Cannot read properties of undefined Data has not arrived yet. Guard with a loading branch or optional chaining
Each child should have a unique "key" A .map() is missing key, or keys are duplicated
Too many re-renders You called a setter during render instead of inside a handler or effect
Objects are not valid as a React child You rendered {someObject}. Render a specific field instead
Rendered more hooks than during the previous render A hook is inside a condition or loop. Hooks must always run in the same order
A component is changing an uncontrolled input to be controlled The value prop started as undefined. Give it an initial value
18

Recap

If you keep six things from this session, keep these.

01

UI is a function of state

Describe the output for the current state. When the screen is wrong, find the wrong state. Do not reach for the DOM.

02

Data down, events up

One owner per piece of state. Children receive values and report intentions. Never mutate a prop.

03

Every fetch has three states

Loading, error, success. Design all three. Server data is a cache of someone else's truth, not your state.

04

Types are a build time contract

They vanish at runtime. Validate at the network boundary where you do not control the shape.

05

Check Storybook first

The component you are about to write may already exist. If it is genuinely new and domain agnostic, add a story.

06

Group by feature

Everything a feature needs lives in its folder. Common code flows downward into features, never the other way.
